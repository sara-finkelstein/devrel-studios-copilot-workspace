## Tooling & Environment

- **Bypass Work IQ path discovery for known Teams and email writes** — unattended agents can receive no search result for valid generic Graph operations even when `create_entity` and `do_action` are available. Call `get_schema` directly for `/chats/{chat-id}/messages`, `/chats/{chat-id}/markChatUnreadForUser`, or `/me/sendMail`, then invoke the corresponding write tool; do not save a self-email fallback as a draft. *Why it matters:* the August 26 publishing watcher detected Episode 236856's `New` to `In Progress` transition but failed to notify until the known Graph paths were called directly.
- **A publishing-state watcher is not a metadata-completeness audit** — Sara's Fabric publishing-ready watcher notifies only when a Publishing child moves from `New` to `In Progress`; it does not inspect blank external title, description, links, chapters, thumbnail, or caption fields. *Why it matters:* Episode 236856 was three days from publication with most external metadata blank, but its Publishing child was still `New`, so no alert fired.
- **Use the live Teams chat message collection for “most recent” requests** — Work IQ conversational search can rank an older semantically relevant message above a newly sent one. Resolve the chat ID, fetch `/chats/{chat-id}/messages` directly, and compare `createdDateTime` before copying anything to ADO. *Why it matters:* on 8/25, search returned Sara's August 18 message to Justin Garrett even though she had sent the authoritative Mahmoud Atallah V2 message at 1:03 PM that day.
- **An open Outlook draft can stay visually stale after a successful Graph update** — if read-back shows the new body but Outlook still displays the old one, create and verify a fresh replacement draft with a new item link rather than asking Sara to trust a refresh. *Why it matters:* the first Golnaz re-review draft remained stale in the open Outlook view even though Graph returned the updated bullet list.
- **Agent-driven scheduled jobs need a machine-readable completion contract** — require `WORKFLOW_STATUS: SUCCESS` only for complete or no-op runs and `WORKFLOW_STATUS: RETRY` for throttled or partial work; the host must exit nonzero when success is absent. *Why it matters:* the August 21 calendar agent described unfinished Graph work but exited normally, which would otherwise suppress Windows Task Scheduler's retry policy.
- **Windows `StartWhenAvailable` does not catch a trigger that predates task installation** — after installing a weekday task later than its scheduled time, run a health check and immediately catch up only newly created tasks whose time already passed. Also retry the specific Copilot package-extraction startup failure. *Why it matters:* the August 21 Fabric V2 and control-tower checks otherwise waited until Monday, and the 4:30 PM calendar job failed before reaching ADO or Outlook.
- **Fabric schedule text can live in either `System.Description` or `Custom.Notes`** — reminder and calendar scans must inspect both fields and stop on conflicting timelines rather than assuming the description is canonical. *Why it matters:* Episode 236856 had its valid V2 deadline only in `Custom.Notes`, so a description-only scan missed it.
- **Split broad ADO MCP reads into smaller batches when a batch fails without details** — first confirm the server with a single-work-item read, then request Episodes and child work items in separate, field-limited batches. *Why it matters:* the August 19 Fabric calendar reconciliation recovered immediately after one oversized mixed-field batch failed, avoiding a false conclusion that the ADO MCP server was unavailable.
- **Use the direct `workiq ask` CLI when the Work IQ MCP surface is unavailable** — the authenticated client can search Sara's calendar, Teams meeting chats, messages, and related Microsoft 365 content while remaining read-only when instructed. *Why it matters:* it reliably found the FEI shorts meeting chat after Outlook COM calendar searches stalled and the browser connection was unavailable.
- **Work IQ can now create, update, read, and delete Outlook calendar events through Microsoft Graph** — validated with a temporary private event on 8/18/26, then deleted it successfully. Use exact skill-owned body markers plus deterministic transaction IDs for Graph upserts and scheduled polling to reconcile later ADO date changes; do not use classic Outlook COM for Sara's normal Fabric calendar sync. *Why it matters:* Graph removes the stuck `OUTLOOK.EXE` cleanup failure and supports reliable live calendar updates without touching the new Outlook desktop process.
- **ADO strips HTML comments from Episode descriptions** — after saving a generated Fabric schedule, ADO can remove the hidden `FABRIC-PRODUCTION-SCHEDULE` markers while preserving the visible heading and timeline. Re-read the description, upsert by the visible `Fabric production schedule` heading plus its following paragraph when markers are absent, and verify exactly one heading remains. *Why it matters:* retrying based only on missing markers duplicated both short schedules before the visible-block fallback was added.
- **Live ADO deadlines override generated schedule text for Outlook calendar dates** — preserve Azure CLI JSON dates as strings in PowerShell with `ConvertFrom-Json -DateKind String`, then parse each populated Due Date as a timestamp, convert it from UTC to Pacific, and only afterward take the local date/time; use the Episode description for intermediate milestones, not to override mapped Editing, Uploading, or Publishing deadlines. *Why it matters:* default JSON parsing can discard the UTC context, and an ADO value such as `2026-08-19T00:00:00Z` is actually August 18 at 5:00 PM Pacific.
- **Official publishing workflows can fail harmlessly in a personal GitHub fork** — the `Bundle KB Plugins Release` workflow requires private `AZURE_ARTIFACTS_CLIENT_ID` and `AZURE_ARTIFACTS_TENANT_ID` repository secrets that are intentionally not copied to forks. A failure in `sara-finkelstein/mvp-copilot-plugins` affects only that fork and does not notify or break the upstream Microsoft repository. *Why it matters:* Sara has no official publishing access and can safely ignore these failures rather than trying to obtain or add publishing credentials.
- **New Outlook calendar writes require a classic-Outlook fallback on this machine** — Work IQ can read the online calendar but its current interface cannot create events, and new Outlook (`olk.exe`) does not support classic COM writes. For calendar automation: try Outlook Online/Graph first; if unavailable, launch installed classic Outlook, save each Exchange appointment in a short-lived process, deduplicate with an exact `BillingInformation` marker filter, close classic Outlook after each save, then verify the result in the running new Outlook UI. *Why it matters:* this reliably created and verified 28 Fabric deadline appointments after broad COM calendar scans repeatedly exhausted Outlook resources.
- **Prefer Outlook Online for email and calendar automation** — use Work IQ/Microsoft Graph first, fall back to desktop Outlook COM only when the online path is unavailable, and always read the saved item back before reporting completion. *Why it matters:* Outlook COM appointment writes were inconsistent during the Fabric deadline-calendar setup, while Sara reports better reliability with Outlook Online.
- **ADO identity fields require organization provisioning before assignment** — adding a person to the DevRel ADO organization may not make them immediately selectable; the identity can remain "unknown" until provisioning completes or the person accepts/signs in. Retry the identity field after propagation, and verify by reading back the display name and email. *Why it matters:* Anita Sheares could not be set as Content Owner immediately after being added, but the same update succeeded about an hour later.
- **Verify communication drafts by reading back the saved item before reporting completion** — generating or composing the text is not proof that an Outlook draft exists. Confirm the exact subject, recipients, body, links, timestamp, folder, and unsent status from the saved item; if any step fails, report it as incomplete rather than success. *Why it matters:* the Episode 233550 V1 review draft was initially reported as created when only an unrelated V2 follow-up was visible, causing avoidable confusion and rework.
- **Copilot CLI plugins cannot be replaced while an active session holds their files open on Windows** — marketplace refreshes can sync the source, but uninstall/update fails with Windows error 32 until every Copilot CLI process using the plugin closes. *Why it matters:* use the scheduled `~/.copilot/bin/update-team-plugins.ps1` maintenance task, which waits for all CLI windows to close and then updates automatically; no Windows shutdown or manual terminal commands are required.
- **Edit open Excel files live via COM instead of closing them** — for this user, prefer `win32com.client` (pywin32, already installed) to attach to a running Excel instance (`GetActiveObject('Excel.Application')`), locate the workbook by name in `excel.Workbooks`, edit cells/ranges directly (`ws.Range(...).Value =`, `.Interior.Color =`, `.Borders`), then `wb.Save()` — all while the file stays open and visible. *Why it matters:* avoids the recurring `PermissionError`/"please close the file" cycle from editing with openpyxl while the workbook is open in Excel; also lets the user watch edits happen in real time. Established 7/20 on the Infra Series Producer Booking Sheet.
- **When reordering rows in Excel, move formatting together with content** — don't reorder by reassigning only `.value`s to different rows; fills/borders/fonts stay attached to the physical row and get silently mismatched with the wrong content otherwise. Move/copy the full row (or explicitly carry over `.fill`/`.border`/`.font` per moved cell) together with values. Formatting tied to a specific person/row should follow that person; only true "structural" formatting (header rows, outlines/borders around the whole table) should stay fixed to position. Exception discovered 7/20: a legacy row highlight got left behind on the wrong guest after an Ep1 reorder (see below) — this is the general rule going forward.
- **openpyxl row reordering moves values but NOT cell formatting/fills** — when reordering rows by reading `.value`s into a list and writing them back to different row numbers (rather than moving whole rows/cells), any fill color, font, or other formatting stays attached to the physical row and does not travel with the content. *Why it matters:* on 7/17, reordering the Infra Series Producer Booking Sheet (moving the ineligible Ep1 row to the bottom) left a pre-existing yellow highlight physically on row 4, which had been on Karthik Uthaman before the reorder — after the reorder, row 4 held Ravi Kiran Reddy instead, so the highlight silently "moved" to the wrong person. Going forward: whenever reordering rows that carry existing formatting, explicitly copy/move fill (and other style) objects alongside the values, or flag to the user that formatting may need manual re-checking after any row reorder.
- **Office files are often IRM/RMS-protected** — many .docx/.xlsx files in Sara's OneDrive/SharePoint (e.g., Book.xlsx, untitled.xlsx, DevRel-Studios-FY26-Impact-Report.docx) are encrypted at rest (OLE2 container with a `DRMEncryptedDataSpace` stream), so tools like pandas/openpyxl/pandoc/the docx & xlsx skills fail with "not a valid Office file" or "not a zip file." *Why it matters:* don't waste time scripting around this — go straight to Word/Excel's native UI (File → Info → Version History, Review → Track Changes) for edit history, authorship, or content on protected files.
- **OneDrive local files are often cloud-only placeholders** — a file can show a tiny size (e.g., 10KB) until opened/copied, which triggers hydration to the real size. *Why it matters:* if a script reads a suspiciously small/corrupt Office file from a local OneDrive path, copy it first (`Copy-Item`) to force download before concluding it's broken.
- **Check the ADO Episode `System.Description` field before assuming title/description are drafts** — it can contain a "status" note (e.g. "This is fully edited and was provided to the team on [date]. We just need final approval.") showing the existing `Custom.Videotitleext`/`Custom.Videodescriptionexternal` are already an approved-in-progress deliverable, not a rough draft to overwrite. *Why it matters:* on 7/21 (episode 228786, dbt + Fabric), this note meant only the missing fields (chapters, resource links) should be written — title/description had to be left untouched even though the metadata pipeline generates its own versions of both.
- **Don't fabricate or guess guest social media profile URLs** — web search often confirms a person's bio/role but can't surface an exact LinkedIn/X profile link in results. *Why it matters:* for episode 228786's speaker social links field, leave it blank and flag for manual confirmation rather than writing an unverified/guessed URL into ADO.

## YouTube Analytics & Content Autopsy

- **[Transcript view vs CC track selection in YouTube]** — transcript panel formatting can look different from active subtitle rendering, and can make a successful upload look "wrong." *Why it matters:* after uploading corrected captions, verify in player CC track selection (e.g., "English (Corrected)") before assuming upload failed.

- **YouTube Analytics API ≠ Data API** — host `youtubeanalytics.googleapis.com`, path `/v2/reports`, scope `yt-analytics.readonly` (msdev token already had it). Returns core metrics, the **audience retention curve** (`metrics=audienceWatchRatio,relativeRetentionPerformance` + `dimensions=elapsedVideoTimeRatio`, 100 points), and **traffic sources**. Query shape: `?ids=channel==MINE&startDate=X&endDate=Y&filters=video==ID&metrics=...&dimensions=...`. *Why it matters:* this is what powers diagnostic post-production analysis beyond vanity metrics; occasional HTTP 500s just need a retry.
- **Thumbnail CTR & impressions are NOT in the Analytics API** — `impressions` and `impressionsClickThroughRate` are rejected as "Unknown identifier" (only card/annotation CTR exists). They also **cannot be derived** — impressions (the denominator) live nowhere in the API and views ≠ impressions. Only source = **YouTube Studio → Advanced Mode → Content → Export CSV**. *Why it matters:* any CTR feature must take a manual Studio export as input.
- **Studio CSV shape & gotchas** — headers: `Content,Video title,Video publish time,Duration,Views,Watch time (hours),Subscribers,Estimated revenue (USD),Impressions,Impressions click-through rate (%)`. The `Content` column = video ID (**trim** the leading space on IDs starting with `-`); row 2 = `Total` (skip). Export has a **row cap** — the Advanced Mode table lazy-loads ~500 rows and exports only what's loaded, so low-view videos get cut. **Fix: filter the table** (Filter box → title contains "X") to export just the target videos. Also: a custom date range needs the **Apply** button or it silently doesn't take. *Why it matters:* saves a lot of re-export churn.
- **Sprinklr dead-end for YouTube CTR** — msdev/"Microsoft Developer" is NOT provisioned to Sara's Sprinklr user (Account filter empty, "No results" for MSDev), and its Social Engagement > YouTube dashboard only carries standard YouTube-API metrics (no thumbnail CTR). *Why it matters:* don't route YouTube CTR through Sprinklr — use the Studio export.

## Work IQ

- **Teams search cannot identify who reacted to a message** — Work IQ can search message text, participants, timestamps, and self-chat content, but does not expose reaction metadata, so a 📌 reaction cannot reliably trigger automation. *Why it matters:* use an explicit self-chat marker such as `#todo Project | Task | due Date`; it is searchable, testable, and avoids false captures.
- **Microsoft To Do custom lists are writable through Outlook COM** — Sara's To Do lists appear as task subfolders under the Outlook mailbox's `Tasks` folder; Outlook COM can create tasks, preserve full URLs/context in `Body`, and set or update `DueDate`. *Why it matters:* this is more reliable and capable than desktop UI automation and should replace the current pywinauto helper for scheduled task creation.
- **Confirm calendar titles before creating invites** — always show Sara the proposed meeting subject and get confirmation; never reuse an existing meeting title merely because the attendees or topic seem related. *Why it matters:* duplicate or series-specific titles can misidentify the meeting, confuse invitees, and create more cleanup than the automation saves.
- **Use Work IQ's direct `/me/events` API when conversational scheduling fails** — check mutual availability first, then create a single Teams event directly with explicit start/end, attendees, body links, and no recurrence. *Why it matters:* the conversational scheduler found the correct slot on 7/24 but failed to return a created event; the direct API completed the invite reliably.
- **No OneNote access via Work IQ** — `search_paths` returns empty for "onenote", "note", "notebook", and "page"; Work IQ's Graph surface doesn't expose the OneNote API at all. *Why it matters:* any "write this to my OneNote" request needs a different mechanism (COM automation or manual paste) — don't waste time retrying Work IQ phrasing.
- **OneNote desktop COM automation is broken on this machine** — `OneNote.Application` dispatches fine, but any real call (`GetHierarchy`, etc.) fails with `Library not registered` / `This COM object can not automate the makepy process`, even after loading the typelib by LIBID (`{0EA692EE-BB50-4E3C-AEF0-356D91732725}`). Looks like a Click-to-Run typelib registration issue, not a code bug. *Why it matters:* don't attempt direct OneNote writes (risk of repeating a prior sync-conflict overwrite) — stage content in a plain file instead and let Sara paste it in herself.
- **Microsoft Teams reactions aren't limited to the standard 6** — tenants with custom emoji reactions enabled (via keyboard/full picker) let users react with a much larger set, e.g. 📌. *Why it matters:* a Teams reaction can be used as a distinctive "capture this" signal without colliding with normal like/heart/laugh usage.
- **Read a spreadsheet's actual rows by passing its file URL** — a plain Work IQ `ask` about presenters in the "Past and upcoming talks" sheet only surfaced 2 of 8; passing the file's SharePoint URL directly via the `fileUrls` parameter made it read the real rows and return all 8 with deck/recording links. *Why it matters:* for guest discovery from the Talks catalog, hand Work IQ the file URL — don't rely on open enterprise search, which misses most rows.

## Office / PowerPoint Automation

- **Download a OneDrive/SharePoint file from a share link (headless)** — in signed-in Edge (Playwright), resolve the file via the shares API: `…/personal/<user>_microsoft_com/_api/v2.0/shares/u!<base64url(sharingUrl)>/driveItem?$select=@content.downloadUrl`. That returns a pre-authenticated `download.aspx?...&tempauth=…` URL you can save with `Invoke-WebRequest`. *Why it matters:* boss's decks/files live in OneDrive, not locally; this grabs them without manual download. (`microsoft-my.sharepoint.com/p/<user>` = that person's personal OneDrive.)
- **Sensitivity-labeled Office files are encrypted at rest** — header `D0 CF 11 E0` (OLE compound file) instead of `PK` (zip). python-pptx / automation CANNOT read them. Fix: open in *desktop* PowerPoint → set a non-encrypting label (e.g. "General") → **Save As** → header flips to `PK` and it's editable. *Why it matters:* internal decks carry MIP labels; must strip before any programmatic editing. (Decryption only happens in memory; saving is what writes unencrypted bytes.)
- **Clone a slide so PowerPoint accepts it: use COM `Slides(n).Duplicate()`, NOT python-pptx XML copy** — python-pptx clones open fine in python but PowerPoint/COM reject them ("PowerPoint could not open the file"). Drive PowerPoint via `pywin32` (`win32com.client.Dispatch("PowerPoint.Application")`), `Duplicate()` the source slide (also copies the slide-level `<p:bg>` background), edit text, `SaveAs(path, 24)` natively. *Why it matters:* reliable, PowerPoint-valid PPT editing. (python-pptx shape-copy misses slide-level `<p:bg>`, causing wrong/grey backgrounds.)
- **Render a PPTX slide to PNG headlessly** — PowerPoint COM `Slides(n).Export(path, "PNG", 1920, 1080)`; needs no other PowerPoint instance running. *Why it matters:* preview slides directly in the terminal.
- **Grab a screenshot straight from the clipboard** — after Win+Shift+S: `Add-Type -AssemblyName System.Windows.Forms,System.Drawing; [System.Windows.Forms.Clipboard]::GetImage().Save($path)` then view the PNG. *Why it matters:* fastest way for Sara to show Copilot what's on her screen — no file save/attach needed.
- **Read Office files that download as OLE (not zip)** — SharePoint/OneDrive downloads here often arrive as OLE2 (`D0 CF 11 E0`) under `.docx`/`.xlsx` names even without a MIP label; python-docx/openpyxl throw `PackageNotFoundError`/`BadZipFile`. Fix: read via Word/Excel COM, or resave to modern format — Excel `wb.SaveAs(path, 51)`, Word save — to flip the header back to `PK` zip so python can parse it. *Why it matters:* lets you programmatically read/parse colleagues' and boss's files.
- **Find anyone's file across M365** — Graph `POST /search/query` with `entityTypes:["driveItem"]` + a name query (via Work IQ `do_action`) returns owner, webUrl, and driveId/itemId fast. *Why it matters:* fastest way to locate "the spreadsheet X uses" without knowing the folder path.
- **Download a cross-user OneDrive file (tokens walled)** — az/CLI Graph tokens are Conditional-Access blocked (403) for other people's OneDrive, and Work IQ reads metadata but not raw bytes. Reliable path: Playwright `browser_navigate` to the file's webUrl in the already-signed-in Edge session — it auto-fires the download; then move it from `.playwright-mcp\`. *Why it matters:* grabbing colleagues' shared files when API tokens are blocked.

## Copilot Tips

- **Use the run-of-show `Live Show` tab as the source of truth for Session IDs** — a workbook's `Video Details` tab can contain different numbering; match titles and speakers against `Live Show` before updating ADO, then follow the Events title convention `[Session ID] Episode title`. *Why it matters:* the MCP Dev Days workbook's Video Details numbering did not match the authoritative Live Show IDs `[100]`–`[107]`.
- **Review generated Episode children immediately after ADO creation** — Studios automation can create Scheduling, Editing, Uploading, and Publishing children even when the requested workflow does not need all four. Verify the generated hierarchy, preserve needed tasks, and remove unwanted branches only after explicit approval. *Why it matters:* the MCP Dev Days Post Event workflow needed Editing, Uploading, and Publishing but not Scheduling.
- **FTTF FY27 Episode defaults must be read from the Show/template before creation** — Show 236193 uses area `Studios\Shows\Fabric Tech Talk Fridays`, iteration `Studios\FY27\H1\Q1`, Swetha Mannepalli as Host 1, Sara Finkelstein as Executive Producer, Matt Scholz as Technical Director, and `Custom.Thumbnails=true`; Content Owner for the SMB Episodes is Anita Sheares. *Why it matters:* create-time area and option fields control child automation, while copying every identity from a prior Episode can incorrectly assign Sara as Technical Director.
- **Fabric publishing weekdays differ by series** — Fabric Tech Talk Fridays publishes on Fridays; Fabric Executive Insights publishes on Tuesdays. Keep the correct series-specific publication weekday when generating or repairing schedules. *Why it matters:* do not apply one Fabric series' publishing cadence to the other.
- **Never create new ADO deadlines in the past** — when applying or repairing a production schedule, preserve an existing deadline if it is due that day; otherwise, do not add an elapsed date and confirm a future replacement with Sara. *Why it matters:* schedules must remain actionable without overwriting valid same-day commitments.
- **[ADO deadlines must be converted from Pacific time to UTC before writing]** — writing `YYYY-MM-DDT00:00:00Z` makes ADO display the previous calendar day in Pacific time, and `az boards work-item update` can apply another local-time conversion to timestamps. Generate UTC from `America/Los_Angeles` and write it through the ADO REST API. Fabric schedule convention: AM = 9:00 AM, midday = noon, EOD = 5:00 PM Pacific. *Why it matters:* prevents one-day-early or wrong-time deadlines across PDT/PST transitions.
- **[FTTF and FEI share an ADO area path]** — Fabric Executive Insights FY27 parent `236171` and its Episodes can use `Studios\Shows\Fabric Tech Talk Fridays`, so area path cannot distinguish the two shows. Validate Fabric schedule eligibility from the parent ID/title instead; known FEI parents are `224267` (FY26) and `236171` (FY27). *Why it matters:* prevents the production-schedule skill from rejecting valid FEI Episodes or misclassifying them as FTTF.
- **[Studios project ingestion should remain Proposal-first]** — do not replace the team's general Proposal intake or approval decision. Start from the approved Proposal, let `Ready for project automation` create the Series/Event/Moment, then use Copilot for detailed project fields, bulk Episode creation, and hierarchy verification. *Why it matters:* removes producer busywork without bypassing governance or duplicating the official intake.
- **[Studios automation is sensitive to create-time fields]** — Series options (Graphics, long-form, Upwork) and Episode options (Shorts, Thumbnails, Upwork, Teleprompter) should be set in the initial create request; changing them later may not backfill children. Standard Episodes generate Scheduling/Editing/Uploading/Publishing, and `Custom.Thumbnails=true` generates a `Thumbnails` child. *Why it matters:* prevents missing deliverables and duplicate-prone manual retries.
- **[Use GitHub checks before the private PR-review skill]** — open a draft PR, wait for GitHub Actions, then run `github-pr-review` locally; fix findings and repeat until the verdict is Approve before requesting boss/team review. *Why it matters:* this reproduced the workflow Golnaz recommended and caught real routing and validation defects in PR #224 before handoff.
- **Bulk Iteration Path change across a show's children** — pull all child IDs via `wit_get_work_item` (`expand: relations`, filter `System.LinkTypes.Hierarchy-Forward`), batch-fetch current `System.IterationPath` for all of them (`wit_get_work_items_batch_by_ids`), skip any already at the target value, then push the rest in one `wit_update_work_items_batch` call (`op: Replace`). *Why it matters:* fast, auditable way to retarget dozens of ADO work items at once (used 7/20 for all 63 non-conforming Fabric Tech Talk Fridays children → `Studios\FY26`); always confirm scope (which work item types) with the user first since it's a bulk write.
- **ADO comments can't be edited via the API** — the `wit_add_work_item_comment` MCP tool only creates new comments; there's no edit/update for an existing one. To amend a note (e.g. add a signature after the fact), post a short follow-up comment referencing the prior one. *Why it matters:* set the full comment (including any required sign-off) correctly the first time to avoid double comments.

- **Installing plugin skills manually** — skills from mvp-copilot-plugins are just folders; download each `SKILL.md` (+ any scripts) into `~/.copilot/skills/`. Shared scripts go in a plugin root (`~/.copilot/plugins/devrel-studios/`) and the `<PLUGIN_ROOT>` placeholder in SKILL.md must be replaced with that absolute path. *Why it matters:* memory storage is blocked (enterprise billing), so durable setup notes belong in these context files, not Copilot memory.

- **Tool awareness rule** — Copilot should always search its available tools before claiming it can't do something. *Why it matters:* prevents wasted time when MCP tools like ADO are available but not discovered
- **Custom instructions** — `~/.copilot/copilot-instructions.md` loads globally; `.github/copilot-instructions.md` loads per-repo. *Why it matters:* per-repo is better for team workflows
- **Launch from workspace folder** — `cd ~\devrel-studios-copilot-workspace && copilot` loads all instructions and context automatically

## Workflow Tips

- **Extend an existing skill when the user intent is the same** — caption proofreading, synchronized caption-format generation, and ADO caption delivery belong in `transcript-proofread`; metadata generation and full video staging remain separate intents. *Why it matters:* avoids overlapping skills that compete for the same request while keeping deterministic format-conversion and ADO-delivery logic in helper scripts.
- **Sync shared repos before skill work** — for `mvp-copilot-plugins`, always fetch/rebase from latest upstream before creating or editing skills, then open PR from the fresh branch state. *Why it matters:* avoids stale-snapshot PRs that regress docs/skill counts and trigger avoidable review churn.
- **Accepting a YouTube collaboration invite (brand channels)** — dotnet, Microsoft Developer, and Microsoft Reactor are all brand channels under Sara's single Google account, so you never sign out or use InPrivate (a private window just starts with no session). To accept: (1) switch the active channel to the collaborator via avatar → switch channel, then (2) open the **collaborator-first** URL `studio.youtube.com/channel/{collaboratorChannelId}/collaboration/{ownerChannelId}`. *Why it matters:* the owner-first URL always shows "Oops, you don't have permission" — both conditions must be true to see the Accept prompt.
- **YouTube API OAuth setup** — run `node ~/.copilot/youtube-tokens/auth.js <channel>` for each channel, authorize in browser, tokens auto-refresh
- **YouTube video stats** — `node ~/.copilot/skills/youtube-description/youtube-api.js <channel> get <videoId>` returns views, likes, comments
